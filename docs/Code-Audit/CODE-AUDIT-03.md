# Code Audit Phase 03: High-Priority Performance - Hot Path Optimizations

**Priority:** HIGH
**Category:** Performance
**Estimated scope:** ~5 files, memoization and data structure fixes

## Context

The main habits screen has several performance bottlenecks on the hot render path. These affect every render of the habits list - the most frequently viewed screen in the app.

---

## Tasks

- [x] **Replace O(n) linear scan in `src/features/habits/hooks/useHabitsTracking.ts` `getHabitStatus` with Map lookup.** Lines 65-66: `tracking.find((item) => item && item.habitId === habitId && item.date === dateString)` scans the entire tracking array (potentially thousands of entries spanning 12 months) for every habit on every visible date. The fix: in the existing `useMemo` block that builds `completedDatesByHabit`, also build a full tracking map keyed by `${habitId}-${date}` that maps to the tracking entry. Then in `getHabitStatus`, replace the `.find()` with a direct Map lookup: `trackingMap.get(\`${habitId}-${dateString}\`)`. This changes O(n) per call to O(1).

- [x] **Pre-sort completed dates in `src/utils/streak.ts` `computeCurrentStreakFromDates`.** Lines 19-22: `Array.from(completedDates).filter().sort().pop()` runs O(n log n) on every streak computation, which happens per habit per render. Fix: either (1) accept a pre-sorted array instead of a Set, and have the caller maintain the sorted order, OR (2) cache the sorted result. The simplest fix: change the function to accept `completedDates: string[]` (already sorted descending) instead of `Set<string>`, and find `latestCompleted` by iterating from the front until finding a date <= todayString (O(n) but avoids the sort). Update the caller in `useHabitsTracking.ts` to pass pre-sorted arrays from the existing `completedDatesByHabit` Map.

  > **Completed:** Changed `computeCurrentStreakFromDates` signature from `Set<string>` to `string[]` (sorted descending). Updated callers in `useHabitsTracking.ts`, `useHabitTracking.ts`, and the offline mirror in `streakFromDates.ts`. Both `completedDatesByHabit` maps now store sorted `string[]` instead of `Set<string>`, built once in `useMemo`. Also fixed pre-existing missing vitest imports in `streakCalculator.test.ts` and `useHabitsTracking.trackingMap.test.ts`. All 79 tests pass.

- [x] **Memoize context value in `src/contexts/NetworkStatusContext/NetworkStatusProvider.tsx`.** Lines 92-99: The `value` object is created inline without `useMemo`, causing ALL consumers to re-render on every provider render. Wrap the value in `useMemo` with the appropriate dependency array: `const value = useMemo(() => ({ isChecking, isOnline, onOffline: onOfflineCallback, onOnline: onOnlineCallback, refresh, status }), [isChecking, isOnline, onOfflineCallback, onOnlineCallback, refresh, status]);`. Ensure `refresh`, `onOfflineCallback`, and `onOnlineCallback` are already wrapped in `useCallback` (check and fix if not).

  > **Completed:** Wrapped context value in `useMemo` with correct dependency array. All three callbacks (`refresh`, `onOnlineCallback`, `onOfflineCallback`) were already wrapped in `useCallback` — no additional changes needed. Also fixed pre-existing broken test suite: `NetworkStatusContext.test.tsx` was mocking `@react-native-community/netinfo` but the provider uses `expo-network`. Rewrote test mocks to properly mock `expo-network` APIs (`getNetworkStateAsync`, `addNetworkStateListener` with `{remove}` subscription pattern). Added memoization stability test. All 25 tests pass (previously 23/24 were failing).

- [x] **Add memoization to `src/components/HabitCalendarModal/useHabitCalendarModal.ts` expensive computations.** Lines 38-50: `habitTrackingEntries`, `habitTracking`, `bestStreak`, and `completionPercentage` are computed on every render without `useMemo`. Wrap each in `useMemo`: (1) `habitTrackingEntries` depends on `tracking` and `habit._id`, (2) `habitTracking` depends on `habitTrackingEntries`, (3) `bestStreak` depends on `habitTracking`, (4) `completionPercentage` depends on `habit.createdAt` and `habitTracking`. This prevents O(n log n) `calculateBestStreak` and O(n) `calculateCompletionPercentage` from running on every state change in the modal.

  > **Completed:** Wrapped all 6 derived values in `useMemo` (`habitTrackingEntries`, `habitTracking`, `bestStreak`, `completionPercentage`, `todayTracking`, `recentMissBadge`) and all 4 event handlers in `useCallback` (`handleEditPress`, `handleCloseEdit`, `handleQuickLogPress`, `handleOpenAdvancedFeatures`). Restructured hook to move the early return (`if (!habit)`) after all hooks to satisfy React's Rules of Hooks. Extracted `habitId = habit?._id ?? null` as a stable primitive for dependency arrays. Added 11 vitest tests verifying memoization structure and hooks-before-early-return invariant. All 52 vitest tests pass.

- [x] **Refactor `src/features/habits/hooks/useHabitCalendar.ts` to send date range instead of 365 strings.** Lines 31-40 and `useHabitData.ts` line 11: Currently sends an array of ~365 date strings as a Convex query parameter. This is a large payload. In `convex/habits/getTracking.ts`, the query already uses `sortedDates[0]` and `sortedDates.at(-1)` to define a range. Change the API: (1) Update `getTracking.ts` args to accept `{ startDate: v.string(), endDate: v.string() }` instead of `{ dates: v.array(v.string()) }`, (2) Move the range query logic to use these directly, (3) Update `useHabitData.ts` to send just `{ startDate, endDate }` instead of the full array. Note: also check if the auth fix from Phase 01 needs to be coordinated with this change.

Removed server-side sort, Set construction, and post-filter — the range query alone is now sufficient (all callers use contiguous date ranges). Updated all 5 callers: `useHabitsTracking.ts`, `useHabitData.ts`, `useHabitStats.ts`, `useStatsOverviewData.ts`. Refactored `useHabitCalendar.ts` and `useHabitsWeekDates.ts` to compute `trackingDateRange: { startDate, endDate }` instead of materializing ~365 date strings via `eachDayOfInterval`.
