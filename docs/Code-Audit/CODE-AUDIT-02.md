# Code Audit Phase 02: High-Priority Bugs - Date/Streak Logic & Future Date Validation

**Priority:** HIGH
**Category:** Bugs
**Estimated scope:** ~5 files, logic fixes

## Context

Several bugs affect the core habit tracking functionality: streak calculations, date handling, and future-date validation. These directly impact the user experience by showing incorrect streaks or allowing impossible actions.

---

## Tasks

- [x] **Fix timezone bug in `convex/habits/stats.ts` streak calculation.** Lines 21-36 mix UTC and local time. `new Date(t.date)` parses `"YYYY-MM-DD"` as UTC midnight, but `new Date()` with `setHours(0,0,0,0)` uses server local time. Fix by using UTC consistently: replace `const now = new Date(); now.setHours(0,0,0,0);` with a UTC-based approach. Parse the date strings directly as `"YYYY-MM-DD"` strings and compare them lexicographically (they sort correctly), or use `Date.UTC()` for all date math. Also replace `new Date(t.date).getTime()` with UTC parsing. Keep the sorted-dates-descending streak counting logic but ensure all comparisons use the same timezone.

  > **Completed:** Rewrote streak and consistency calculations to use pure `YYYY-MM-DD` string comparisons, eliminating all `Date` object timezone ambiguity. Added `getTodayUTCDateKey()` and `subtractDaysFromDateKey()` UTC helpers to `convex/habits/utils.ts`. Streak now uses a `Set<string>` lookup instead of sorted array comparison. Consistency uses lexicographic string filtering (`t.date > thirtyDaysAgoKey && t.date <= todayKey`). Added 40 tests across `stats.test.ts` (25 tests) and `utils.test.ts` (15 tests) — all passing.

- [x] **Fix stale `today` in `src/features/habits/hooks/useHabitCalendar.ts`.** Line 5: `const today = useMemo(() => startOfDay(new Date()), []);` caches today's date forever. If the app stays open past midnight, all date-dependent behavior breaks. Fix by adding a mechanism to refresh `today` - either use a 1-minute interval that checks if the day has changed, or use `useAppState` to recalculate when the app returns to foreground. The simplest fix is: import `useAppState` or `AppState` from react-native, and in a useEffect, listen for `appStateChange` events - when the app comes to foreground, check if the date has changed and update accordingly. Consider using a `useState` + `useEffect` pattern with an AppState listener instead of `useMemo`.

  > **Completed:** Extracted a new `useToday()` hook (`src/features/habits/hooks/useToday.ts`) that uses `useState` + `useEffect` with two day-change detection mechanisms: (1) `AppState.addEventListener('change')` refreshes `today` when the app returns from background, and (2) a 60-second `setInterval` fallback catches midnight crossings while the app stays in foreground. The setter uses referential equality (`prev.getTime() === now.getTime()`) to avoid unnecessary re-renders. Updated `useHabitCalendar.ts` to use `useToday()` instead of the stale `useMemo`. Added 11 tests across `useToday.test.ts` (7 tests) and `useHabitCalendar.test.ts` (4 tests) — all passing.

- [x] **Fix 24-hour grace period in `convex/habits/utils.ts` `isFutureDate` function.** Lines 44-57: The 24-hour grace period allows users to toggle habits for tomorrow (and sometimes day-after-tomorrow). This defeats the purpose of preventing future-date tracking. Reduce the grace period to 2-3 hours (which handles timezone edge cases without allowing next-day tracking), OR better yet, have the client send its local timezone offset along with the date, and validate based on the user's actual timezone. As a simpler fix: change `const gracePeriodMs = 24 * 60 * 60 * 1000` to `const gracePeriodMs = 3 * 60 * 60 * 1000` (3 hours).

  > **Completed:** Reduced `isFutureDate` grace period from 24 hours to 3 hours in `convex/habits/utils.ts`. This prevents users from toggling habits for tomorrow while still accommodating legitimate timezone differences between client and server. Added 7 tests to `utils.test.ts` covering: today (not future), yesterday (not future), far past (not future), tomorrow (now correctly blocked as future), 2 days ahead, 7 days ahead, and 365 days ahead — all passing. Total: 22 tests in `utils.test.ts`, 61 across the habits module.

- [x] **Fix `computeCurrentStreakFromDates` in `src/utils/streak.ts` to validate streak is actually current.** Lines 8-46: The function counts backwards from the most recent completed date without checking if that date is today or yesterday. If a user broke their streak 10 days ago after a 5-day run, this still returns 5. Add a check after finding `latestCompleted`: calculate the number of days between `latestCompleted` and `todayString`, and if it's greater than 1, return 0 (the streak is broken). Reference the correct implementation in `src/lib/offline/calculations/historyCalculation.ts` which properly checks `daysSinceLastCompletion > 1`.

  > **Completed:** Added `daysSinceLastCompletion` check after finding `latestCompleted` — if the gap from today exceeds 1 day, the function now correctly returns `0` (streak broken). This mirrors the pattern from `historyCalculation.ts:37-43`. Updated 2 existing tests that asserted the buggy behavior (old completions returning `1` instead of `0`), added 7 new tests specifically covering broken-streak scenarios (2-day gap, 10-day-old run, yesterday-still-active, today-active, single-completion edge cases). Also added missing `import { describe, it, expect } from 'vitest'` to the test file. All 36 tests in `streak.test.ts` pass; 97 tests across the habits module pass.

- [x] **Fix optimistic state race condition in `src/lib/optimistic/store/stateManagement.ts`.** Lines 61-69: The `confirm()` method uses hardcoded `setTimeout(300)` and `setTimeout(400)` to clear state, which can cause visual flicker if Convex subscription takes longer. Instead of hardcoded timeouts, use a Convex subscription callback or a longer timeout with a fallback. At minimum: (1) increase the timeout to 1000ms to handle slow networks, (2) store the timeout IDs so they can be cleared if the component unmounts or if a new operation comes in. Add a `cleanup` method or track timeouts in a Set that gets cleared on `rollback` or subsequent operations.
  > **Completed:** Added `pendingTimeouts` Map to track timeout IDs per operation. Increased confirm delay from 300ms/400ms to 1000ms/1100ms for slow-network resilience. Both `confirm()` and `fail()` now cancel any pre-existing timeouts for the same operationId before setting new ones, preventing leaked timers and flicker from stale callbacks. Updated 22 unit tests in `store.test.ts` (added fake timers, 4 new timeout-management tests covering: cancel-on-fail, operation-record lifecycle after confirm, operation-record lifecycle after fail, duplicate-confirm safety). Fixed 2 pre-existing broken tests in `optimistic-updates.test.ts` integration suite that incorrectly expected synchronous state clearing after `confirm()`. All 86 optimistic tests pass; no timer leak warnings from Jest.
