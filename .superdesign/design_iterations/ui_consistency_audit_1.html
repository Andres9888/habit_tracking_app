01

Press feedback drifts per component

Critical · felt on every tap

Five different press scales are in the codebase (0.90 / 0.92 / 0.95 / 0.96 / 0.97 / 0.98), applied through three different mechanisms — usePressAnimation, ad-hoc withSpring, and raw withTiming(…, {duration: 50}). Tap the cards below. The "before" pane is the app today.

One physical law for the whole app. Press depth encodes nothing — so the eye stops decoding it and just reads content.

Why this matters

Press feedback is the app's handshake — it fires hundreds of times per session and is the single most-repeated micro-interaction. When the same gesture returns six different physical responses, users can't build a motor model of the interface. It reads as unfinished long before anyone can name why.

It is also the cheapest fix in this document: springs.standard and AnimatedPressable already exist and already handle focus rings, 44pt hit-slop and reduced motion. The work is deletion, not authoring.

Why this matters

Dwell time is a promise about how long the user has to act. Today it varies from 2s to 8s with no rule behind it, so an undo affordance can vanish faster than a purely informational message. That's not inconsistency — that's a usability defect wearing inconsistency's clothes.

Collapsing to one <Toast intent> also deletes ~7 animation hooks and ~600 lines, which directly serves the ≤100-line file ceiling in CLAUDE.md.

03

List entrance ignores its own spec

High · first impression

theme/animations.ts states the rule at the top of the file: "280ms cubic ease-out, 60ms stagger, max 5 items, no springify." In practice FadeIn.duration(300) appears in 7 files, .duration(150) in 7 more, and stagger is uncapped — so a 20-habit list animates for 1.2 seconds before it settles.

Before — todayuncapped stagger · mixed durations
Today
8 items × 60ms stagger + 300ms = 720ms tail
After — proposed280ms · stagger capped at 5
Today
Items 6+ inherit index 5's delay → 560ms total, always

Why this matters

Stagger is a hierarchy cue — it tells the eye "these arrived together, in this order." Past roughly five items it stops communicating and becomes a wait. The spec already caps it at 5; the code just never enforced the cap, so entrance cost scales linearly with how successful the user is at using the app. The person with 20 habits — your best user — gets the worst launch.

Why this matters

The decomposition initiative in CLAUDE.md pushes files under 100 lines. Consolidation is the version of that which reduces total lines rather than redistributing them.

05

Reduce Motion is honoured in 20 of 88 animated surfaces

High · accessibility

useReduceMotion exists and is wired correctly into useFocusRing, useHaptics and HabitCard's celebration. But of the 88 files using entering=, 68 animate unconditionally. Toggle the switch in section 01 and re-tap — the "after" pane responds, the "before" pane does not.

Why this matters

For users with vestibular sensitivity, the 4×50ms error shake on the habit-name field is the worst offender in the app — it fires on a validation failure, exactly when someone is already frustrated, and there is no way to turn it off. That's a shipping accessibility bug, not a polish item.

The fix is a single wrapper: route every entering= through one useEntrance() helper that already reads the preference. Then reduce-motion coverage becomes structural rather than per-author memory.

Why this matters

The inline hex colors are the urgent subset. darkColors.ts exists and dark mode is applied at render time via useThemeColors() — any literal #RRGGBB in a StyleSheet silently opts that element out. Those ~120 sites are dark-mode bugs that haven't been reported yet.

The rest is a slow leak: airy.ts is designed as a single lever that rescales the whole app (AIRY_SCALE = false restores canonical). Every hardcoded radius and pad is a piece of UI that lever no longer reaches.

The plan

Sequenced so each phase makes the next cheaper

Ordered by felt impact per unit of risk. Phases 1 and 2 are mostly deletion and are independently shippable. Phase 0 is what prevents all of this from regrowing.

PHASE 0

Close the tap — enforcement before cleanup

  • ESLint no-restricted-syntax: literal duration:, damping:, #hex in StyleSheet.create → error
  • ESLint no-restricted-imports: raw Modal from react-native outside components/Sheet
  • Warn on <Pressable with onPress outside components/ui
  • Ship as warn, same ramp the max-lines rule used
~0.5d
zero risk
PHASE 1

Unify press feedback & entrance

  • Delete all ad-hoc press scales → AnimatedPressable / Button (§01)
  • Add useEntrance() wrapping useReduceMotion + durations.enter + capped stagger (§03, §05)
  • Kill the 4×50ms name-field shake — replace with color + icon (§05)
~2d
highest felt gain
PHASE 2

Collapse the toast family

  • One <Toast intent="info|undo|celebrate"> · one animation hook
  • Dwell becomes a function of intent, not of author (§02)
  • Migrate 7 call-site families; delete ~600 lines
~2d
net line reduction
PHASE 3

Dark-mode-breaking color literals

  • ~120 production inline hex → colors.* / useThemeColors()
  • Start with QuickActionsSheet/ActionItem, AchievementCard, InfoModal
  • Screenshot diff in dark mode as the acceptance gate
~1.5d
fixes latent bugs
PHASE 4

Button & Sheet consolidation

  • 37 button components → Button variants; keep only genuinely-domain ones (FloatingActionButton, SwipeableActionButton)
  • 42 raw <Modal> → <Sheet> with shared backdrop, detents, gesture dismiss
  • 12 empty states → EmptyState; 4 section headers → one
~5d
largest, do last
PHASE 5

Codemod the remaining scalars

  • Automated padding/margin/fontSize/borderRadius → tokens
  • Flip every Phase 0 ESLint rule from warn to error
~1d
mechanical

Why this order

Phase 0 first because cleanup without enforcement regrows — the theme files already prove the app knows the right values and drifts from them anyway. Phase 4 is deliberately last: it's the largest diff and the most merge-conflict-prone, and it becomes far cheaper once Phases 1–2 have already established what the shared motion contract is.

Phases 1, 2 and 3 are each independently shippable and independently visible. Nothing here requires a redesign — the design already exists in src/theme/. This is the app learning to speak it.
