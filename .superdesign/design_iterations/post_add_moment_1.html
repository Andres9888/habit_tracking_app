Why change it

Everything below is checked against the code as it exists today, not against a description of it.

a. What's wrong with the BEFORE

  1. The CTA slot stops being a control. On success FooterPrimaryAction.tsx:37-61 swaps the pressable for a plain Animated.View — same 56px pill, same weight, same position, but it has no onPress, no accessibilityRole, and the word on it is Added. The most prominent element on the screen is now inert. Marker A in the BEFORE frame.
  2. The only permanent route is backward. FooterSecondaryActions.tsx:44,65 relabels the secondary link to "Find another habit" and points it at onDone, which PreviewContent.tsx:75 wires to handleDismiss — back to the library. So the durable post-add affordances are: an inert pill, and a door back to browsing. Marker B. (Worth noting: the row no longer unmounts — its own docblock at FooterSecondaryActions.tsx:5-8 records that fix. The dead end is now a routing problem, not a missing-element problem.)
  3. The one forward route is on an 8-second timer. TemplateAddedToast.tsx:96-121 renders "View my habit" and "Add another", but the toast auto-dismisses after DEFAULT_DURATION = 8000 (TemplateAddedToast/constants.ts). It is also a transient overlay pinned to the bottom of the screen, sitting directly on top of the footer it is competing with. Marker C. After eight seconds the screen is the dead end again.
  4. The good post-add experience exists, but only once per account. useImportFeedback.ts:49-53 routes to MakeItStickSheet only when habitCountRef.current === 0. That sheet is exactly the right moment — cue anchoring, a realistic expectation, an identity line (MakeItStickSheet.tsx:1, MakeItStickSheet.helpers.ts:7-12). Habit #2 onward never sees it.
  5. The habit-named toast copy never renders on the success path. useImportFeedback.ts:59-65 sets toastMessage to `${t.name} is on your list`, but FeedbackOverlays.tsx:39-49 branches on toastTemplateData — which the same function just set to a non-null object — so success always renders TemplateAddedToast, whose title is built internally as Added 'Meditate' to your habits (TemplateAddedToast.tsx:40-43). toastMessage only reaches the error Toast. The BEFORE frame shows what actually renders.
  6. Nothing about the habit is decided. The habit is created with template defaults. No time, no cue, no anchor. The one screen where the user is most willing to answer "when does this happen?" asks them nothing.

b. What the AFTER does differently

  1. 1The confirmation becomes a line of text, not a fake button. "Meditate is on your list" — the copy already written at useImportFeedback.ts:63, finally on screen. It sits in a card at 17px with a small green check, so nothing in the footer looks pressable unless it is.
  2. 2One sentence of reason, no hype. "It sticks better after something you already do. Pick a moment — you can change it later." It explains the ask and pre-forgives the answer. No streak language, no confetti, no countdown.
  3. 3Cue chips, inline, for every add. The same implementation-intention options MakeItStickSheet already builds (MakeItStickSheet.helpers.ts:7-12: template suggestedCue first, then two defaults), pre-selecting the first exactly as MakeItStickSheet.tsx:35-37 does. Three chips, one of them "Something else…". This is the ungating: the first-habit-only sheet becomes the every-habit footer step.
  4. 4The primary CTA stays a CTA. Same 56px pill, same #2FA36F, same slot — the label moves from "Add this habit" to "Lock it in" (the verb StickActions.tsx already uses). The user's thumb does not have to move, and the strongest element on the screen keeps doing work.
  5. 5A forward exit that doesn't expire. "See it in my habits" routes through the onViewHabit path that already exists end-to-end (useLibraryScreenActions.ts:40-43 → TemplatesModalSection.tsx:31-36) — but as a permanent link on the screen instead of a pill inside an auto-dismissing toast.
  6. 6The backward route is kept and demoted. "Keep browsing" is the same onDone/handleDismiss behavior as today, now one of two quiet links rather than the only thing offered. Browsing on is a legitimate choice; it just isn't the default.

Also proposed, and visible by its absence in the AFTER frame: no toast on this screen. The detail view can confirm in place, so TemplateAddedToast would fire only for adds made from the catalog grid (onPopularImport), where there is no footer to hold the confirmation. Today the toast and the "Added" pill say the same thing twice, one of them on a timer, stacked on top of each other.

c. What gets better for the user

  • The habit gets scheduled instead of orphaned. Today habit #2 onward lands in the list with template defaults and no anchor. The AFTER asks one question, with the answer pre-filled, at the only moment the user is holding the whole context in their head. A habit with a cue attached is a habit with a trigger; one without is a row in a list waiting to be noticed.
  • Intent doesn't have to survive a timer. The forward route stops being a transient overlay. Nothing important disappears while the user is still reading the screen — which matters most for the slower, more considered readers who scrolled the evidence section before adding.
  • The exit is a choice, not a default. When the only durable affordance points back to the library, going back is what most people do — not because they wanted more habits, but because it was the thing on offer. Adding five unanchored habits in one session is the failure mode this shape quietly encourages.
  • The screen stops contradicting itself. An inert pill styled like the button that was there a second ago teaches people that tapping did nothing. A sentence plus a live button reads correctly on first glance.
  • The good experience stops being a one-time event. The cue step already exists and is already written in this app's voice. It currently fires once per account. Reusing it per-add is mostly a gating change, not new surface area.
