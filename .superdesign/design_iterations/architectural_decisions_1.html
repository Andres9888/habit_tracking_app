Wave 3.1 · Architectural · New component
Unified Button primitive
~1–3 days · low–medium risk
Today
290 files use inline Pressable/TouchableOpacity. Only 4 dedicated button folders (Button, QuickCompleteButton, SwipeableActionButton, ForceUpdateButton). Padding combinations: 10+ distinct (px-4 106×, px-3 44×, py-3 48×, etc.).

The existing Button component already exists with large/medium/small sizes and primary/secondary/ghost/icon variants in componentSpacing.button. The proposed primitive isn't new design — it's adoption.

A Adopt the existing Button primitive — opt-in Recommended

Document Button in a brief migration guide. Migrate when files are touched for other reasons. New code MUST use the primitive. Lint rule (no-restricted-syntax) flags new Pressable usage outside components/Button/ and a small allowlist of feature-specific buttons.

  • Zero immediate risk — no bulk migration
  • Stops bleeding (new code is consistent)
  • Migrations happen with proper QA per touched file
  • Long-tail; complete adoption takes months
  • Two patterns coexist for a while
B Bulk-migrate top 30 highest-traffic Pressable sites

Audit the 30 sites with most app-time render frequency (Habit list, daily completion, bottom action bar, header buttons). Migrate them in one PR. Leaves 260+ inline.

  • Visible adoption gain (top sites = most-seen UI)
  • Forces real-world stress test of primitive
  • Big PR (30 files × component swap)
  • Each touched site needs visual QA
  • Without `.env.local` I can't visually validate
C Replace with library (gluestack / tamagui)

Adopt a third-party component library, deprecate custom Button.

  • Vendor-maintained, accessibility built-in
  • Brings other primitives (Modal, Sheet, Input) for free
  • Adds a major dependency
  • Existing warm-minimal aesthetic needs theming work
  • Largest scope — multi-week project
Pick A · B · or C
My pick: A. The Button component already exists; this is an adoption problem. A lint rule plus a docs page closes the gap with zero risk to shipped surfaces.

Wave 3.3 · Migration · Motion
Animated.Value → Reanimated
~3–5 days · high risk (motion QA)
Today
31 files use legacy new Animated.Value(...) (JS thread). 516 files use react-native-reanimated (UI thread). Mixed APIs in the same app create motion personality drift and maintenance overhead. 14 remaining sites use legacy Animated.spring({ friction, tension }). 
// Legacy — runs on JS thread, can stutter under load
const scale = useRef(new Animated.Value(1)).current;
Animated.spring(scale, { friction: 8, tension: 200, toValue: 0.95 }).start();

// Reanimated — runs on UI thread, smoother under load
const scale = useSharedValue(1);
scale.value = withSpring(0.95, springs.standard);
A Migrate all 31 files in one focused sprint

Multi-day effort with motion QA per component. High risk because legacy files often use bespoke timing the developer hand-tuned.

  • Single API across the codebase
  • UI thread → smoother animations under load
  • Each file needs visual QA
  • Without `.env.local`, I can't validate
  • Risk of motion personality drift
B Migrate-on-touch + lint rule for new code Recommended

Add ESLint rule banning new Animated.Value in new code. Migrate only when files are touched for other reasons. Same opt-in pattern as Wave 3.1.

  • Stops bleeding without risk
  • Migration happens alongside actual feature QA
  • No motion regressions in shipped paths
  • Long-tail — full adoption takes months
C Leave alone — it works

Animated.Value works fine for these 31 files. Don't migrate.

  • Zero risk
  • Mixed APIs forever
  • Loses UI-thread perf for those animations
Pick A · B · or C
My pick: B. Same reasoning as Wave 3.1 — adoption problems are best solved with lint rules + organic migration, not bulk sweeps that need motion QA you can't run today.
Wave 3.4 · Architectural · Conversation
NativeWind vs StyleSheet — pick one
~conversation + multi-week if migrating
Today
303 files use NativeWind className= with rounded values. 382 files mix className AND style={{}}/StyleSheet. Same component often has both. Tailwind's spacing scale doesn't always match the theme tokens (e.g., borderRadius.card = 16 vs Tailwind's rounded-lg = 8). 
// Mixed today — same component
<View
  className="flex-row items-center gap-2 px-4 py-3 rounded-lg"
  style={[styles.card, { backgroundColor: colors.surface }]}
/>
A Pick StyleSheet + theme tokens — deprecate className

All future code uses StyleSheet.create with theme tokens. NativeWind gradually removed. Theme is the single source of truth.

  • Theme tokens always win — no Tailwind drift
  • Easier to enforce design system
  • Better TS autocomplete
  • NativeWind is faster to write
  • Removing it is multi-month migration
B Pick NativeWind v4 — extend Tailwind config to mirror theme

Sync tailwind.config.js exactly to theme tokens (already partially done). Deprecate StyleSheet for new code.

  • Faster to write component styles
  • Smaller diffs in PRs
  • Two type systems — hard to refactor tokens
  • Tailwind extends slowly when design system grows
C Document boundary rules — keep both Recommended

Write a one-page convention doc: className = layout/spacing/Tailwind utilities (flexbox, padding, gap, position). StyleSheet + tokens = component-specific styles (colors, borders, shadows, typography). Theme tokens always win over className.

  • Zero migration cost
  • Plays to each system's strengths
  • Most React Native + NativeWind apps work this way
  • Boundary requires discipline (lint rule helps)
D Migrate to tamagui or unistyles — biggest lift

Replace both with a unified styling system. Multi-month project.

  • Major dependency
  • Largest scope
  • Untouched theme system gets rebuilt
Pick A · B · C · or D
My pick: C. The mixed pattern isn't actually bad if the boundary is clear. Most teams that have tried to "pick one" end up regretting it. Document the rule, add a lint check that warns when className includes color/border tokens (those should be StyleSheet).

Wave 2.5 · Long-tail cleanup
Raw hex cleanup (757 sites)
~varies by approach
Today
757 raw hex values remain in components (down from 1,101 at Apr 23). Many are intentional: gradient endpoints, achievement palettes, material tier ramps, category colors, confetti particle colors. Others are real drift (one-off colors that should be tokenized).

The hard part is intent inference. '#FFD700' in a trophy badge is intentional (gold). '#a8a29e' in a generic component is drift (should be colors.gray[400]). I can't tell programmatically.

A Component-by-component manual sweep

Multi-week. Each hex value gets a per-case decision.

  • Largest scope
  • Many decisions are subjective
B Define semantic palette tokens for the most common intentional groups Recommended

Add 3 new namespaced palettes to the theme:

  • colors.parchment.{50,100,200,300,400} — warm motivation surfaces (used in GoalWhyAnchor today)
  • colors.tone.{green,red,orange,yellow,blue,purple} — semantic tone for GoalCoachLine, achievements
  • colors.material.{copper,bronze,silver,gold,legendary} — habit chain progression tiers

This formalizes ~150 of the 757 hex values into named tokens. The remaining 600 are gradients/one-offs that stay raw.

  • Codifies intentional design choices
  • Sets up for dark mode (each namespace can have a dark variant)
  • Reduces 757 → ~600 with named meaning
  • Token namespace decisions need design review
C Leave alone

757 raw hex isn't great but it's not blocking. Defer until dark mode work resumes.

  • Zero risk now
  • Dark mode unlock will surface them all at once
Pick A · B · or C
My pick: B. Defining the three semantic namespaces (parchment, tone, material) is the highest-ROI move because it makes dark-mode unlock tractable later. Without namespaces, dark-mode work has to grep 757 hex values one by one. With namespaces, you flip the namespace and ~150 sites update.
